# i18n — Langue d'interface

L'interface propose un **sélecteur de langue**, avec pour l'instant **EN** et **FR**. Il gouverne le
**chrome** (libellés de l'application), **jamais** le contenu écrit par l'auteur.

> **Statut : exigence MVP à cadrer.** Le sélecteur EN/FR est acté côté produit ; la mécanique exacte
> (notamment la source des labels de types/champs, voir §3) reste un **point ouvert** à trancher, si besoin
> par un ADR. Ne pas confondre avec [ADR 0010](../adr/0010-frontmatter-keys-en-content-fr.md), qui fixe les
> **clés** de frontmatter en anglais et le **contenu** en français.

## 1. Ce qui est traduit / ce qui ne l'est pas

| Catégorie | Langue | Exemple |
|---|---|---|
| **Chrome de l'app** (menus, boutons, en-têtes de section, messages d'état, tooltips) | **Traduit** (EN/FR) | « Nouvelle entrée » / « New entry » |
| **Labels de types & de champs** (affichés) | **Traduit** (EN/FR) | `role` → « Rôle » / « Role » |
| **Clés de frontmatter** (techniques, repère mono) | **Jamais** — toujours EN `snake_case` | `role`, `pov`, `ruling_faction` |
| **Contenu de l'auteur** (`title`, valeurs, corps, tags, aliases) | **Jamais** — tel qu'écrit | « Aria Solane », « protagoniste » |
| **Slugs / chemins / dates ISO** | **Jamais** — techniques | `aria-solane.md` |

Principe : on traduit ce que **l'application** dit, pas ce que **l'auteur** a écrit. Un projet FR reste FR
même si l'UI est passée en EN — seul le chrome change.

## 2. Emplacement & comportement

- **Sélecteur** dans la topbar (près du thème) ; à terme, doublé dans un écran Réglages.
- Deux entrées au MVP : **FR** (défaut si locale système FR) et **EN** (fallback). Extensible.
- La langue est une **préférence locale** (comme le thème), pas une donnée du projet : elle ne s'écrit pas
  dans les fichiers markdown et ne rend pas le projet moins portable.
- **Formats locaux** : dates affichées et nombres suivent la langue choisie (les dates **stockées** restent
  ISO 8601 / RFC 3339 — [data-model.md](../data-model.md) §2).

## 3. Point ouvert — source des labels de types/champs

Aujourd'hui, `GET /types` renvoie un `label` **en français uniquement** (`FieldSchema.label`,
`TypeResponse.label` — [api.md](../api.md)). Pour une UI EN, deux voies possibles :

1. **Backend localisé** : `/types` renvoie les labels selon `Accept-Language` (ou un paramètre `lang`),
   Storyteller gardant un catalogue EN/FR des labels intégrés.
2. **Catalogue front** : le backend ne renvoie que la **clé** (`name`), le frontend porte son propre
   dictionnaire i18n (chrome **et** labels de types/champs intégrés).

Recommandation à confirmer : **catalogue front** pour le chrome (inévitable de toute façon), et labels de
types/champs **intégrés** côté front tant que les types restent ceux, fixes, du MVP — en réévaluant si/quand
arrivent les **types et champs personnalisés** (aujourd'hui « later », [features.md](../features.md) §B), qui
imposeraient une source de labels côté données.

## 4. Conséquences UI

- Les libellés ne doivent jamais être **codés en dur** dans les composants : passer par des clés de
  traduction, y compris pour les messages d'état ([states.md](states.md)) et les labels de champs.
- Prévoir l'**élasticité** : un même libellé varie en longueur entre EN et FR (les boutons et colonnes ne
  doivent pas casser).
- Le repère **mono** de la clé technique (ex. `pov`) reste affiché à côté du label localisé, ce qui aide à
  faire le lien avec le fichier .md quelle que soit la langue.
